What was wrong?

“No time-aligned visible speaking face” rejected the sentence before final acoustic identity resolution. It did not mean that the name Christoph failed to parse. The 10-Hz visual detector required unusually large per-frame lip movement and multiple reversals in a 700-ms window. A modest 2-Hz articulation fixture was rejected by that rule. The browser also accumulated its packet counter across reconnects while the server reset its seconds counter.

Changes

  • 800-ms temporal window, motion per second, hysteresis and excursion/reversal checks; a secondary normalized lip-width cue. No extra model, GPU use or face upload.
  • Static mouths, small jitter, one opening held open, slow non-speech movement and rigid translation/scale remain negative controls. This is a heuristic, not proof that sound came from the face.
  • Missing timestamps, missing faces and insufficient mouth activity have different recovery messages. Invalid timestamps cannot keep a camera observation fresh.
  • The recovery button automatically appears in the expanded microphone panel. It disables only the camera/offscreen filter, preserving the voice recognition setting, camera and gaze. It asks for a new introduction, without replaying a rejected turn or guessing a face binding.
  • Per-connection microphone counters now match the server session. Voice-match threshold remains 0.32; no identity check was bypassed.

End-to-end browser checks

Actual public HTTPS page, Chrome capture worklet, ASR, speaker enrollment, Luna and streamed TTS. Facial landmarks are synthetic and processed by the actual JavaScript mouth-motion detector; speaking flags are not injected. Synthetic movement follows the fixture's captured speech, not an assumed file start time. The session is opened before starting the fake microphone so the fixture's wake phrase is not lost during connection establishment. A 35-second deadline prevents success by automatic fixture looping.

Limits and retained failures

No physical recording of the user was available, so human webcam recognition accuracy, lighting robustness and true A/V offset are not claimed. Real MediaPipe and face-api CPU smoke tests use public still imagery; the live onboarding test uses artificial moving landmarks. Chewing and other plausible mouth movements can resemble speech. Multiple overlapping faces remain uncertain. An initial harness assumed the fake file started with the WebSocket clock and failed; another run only enrolled on the file's second loop. A separate failed browser run exposed the recovery button hidden inside a collapsed panel, which is now automatically opened. Those receipts are retained locally rather than counted as passes.

To try the fix: reload the page, start talking, wait for readiness, face the camera and say “Hi Robbie, I am Christoph.” If the visual filter still rejects the sentence, use Use voice recognition without camera filtering and repeat. This leaves acoustic recognition active, rather than using “Talk without speaker filter.”
